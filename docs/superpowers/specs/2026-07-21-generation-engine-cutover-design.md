# Generation-engine cutover — design

**Date:** 2026-07-21
**Status:** design approved, pre-implementation
**Supersedes sequencing in:** `docs/phase7_generation_engine_plan.md` (that plan's own text: "no
implementation until this is reviewed and agreed" — this document is that agreement, with the
sequencing and end-state revised per the decisions below).

## Motivation

MinusOps composes generated Terraform almost entirely from a fixed catalog of 16 hand-written
modules under `modules/<id>/` (`core/generation/modules.py:match_modules()` picks by keyword
score). That catalog is the "hardcoded boilerplate" this design replaces. The goal: for a given
set of requirements, the engine researches the real, current shape of the resources it needs
(live Terraform provider schema + docs) and authors HCL grounded in that research, rather than
selecting from pre-written files — then deletes the pre-written files once the new path is proven
to cover everything they did.

Grounding documents (read, not re-derived here):
- `docs/generation_engine_ground_truth_survey.md` (2026-07-15) — what exists today, verified
  against code, not memory.
- `docs/phase7_generation_engine_plan.md` — the original 5-item sequencing this design revises.
- `docs/generation_pivot_first_proof_2026-07-18.md` — one real proof that agent-authored HCL can
  pass the full gated path today (hand-authored, not generated by this engine).

## Decisions (from design dialogue, 2026-07-21)

| Question | Decision |
|---|---|
| Catalog's long-term fate | Retired, not kept as permanent fallback — a bridge, not a destination. |
| Who performs "research" | Automated schema fetch (deterministic code) feeding an LLM that authors the HCL — not the LLM fetching docs pages itself each time, not fully rule-based generation. |
| What "preplan" means | Decide which resource types are needed, from the *full* requirements record — not just keyword matching or the two currently load-bearing fields (`data_volume`, `budget`). |
| Requirements-schema question (Phase 7 item 3) | Resolved as branch (a): make the schema real input. Preplan must read `functional`, all `data_pipeline` sub-fields, and all six NFR axes, not just two fields. |
| What "validate" covers | G2 schema lint + offline `terraform validate` (existing) **plus** a G9 ephemeral apply against MiniStack and Floci (the two free/no-token emulators in `core/governance/ephemeral_apply.py`) for fidelity evidence — not a live plan against a real AWS account. |
| Catalog retirement trigger | Objective, not vibes: a resource type graduates after 3 clean passes — generated, G2-clean, `terraform validate`-clean, MiniStack+Floci-clean, zero manual correction — recorded per module, still requiring explicit human sign-off before deletion. |
| Cutover timing | Build the full engine, prove parity against all 16 modules' current capability, delete the catalog in one commit. No incremental deletion, no window where a pipeline that worked yesterday stops working. |

## Non-goals

- Azure/GCP generation. Stays AWS-only, matching every other part of the codebase's current scope
  (`core/providers/azure.py` / `gcp.py` remain honest roadmap scaffolds, untouched).
- Any change to the deploy gate's authority. G2/G5/G6/G9 remain the only path anything ships
  through. This engine produces candidate HCL; it never applies anything, same as today's
  `authored_content` seam.
- Making generation the default composition path before parity is proven. Until sub-project 6
  closes, the catalog keeps composing exactly as it does today.

## Architecture — end state

```
requirements.json (full record)
        |
        v
   preplan()  --------------------------> resource_type list
        |                                  (sub-project 3)
        v
   research(resource_type) ---> {schema: live provider attrs, docs: registry/AWS urls}
        |                        (sub-project 4, composes schema_watch + schema_lint + discovery.py)
        v
   author(resource_type, research) ---> module-shaped HCL
        |                                (variable/output/locals/companion assets — sub-project 1)
        |                                (LLM-written, grounded in research — sub-project 5)
        v
   validate(hcl) ---> G2 lint -> terraform validate -> MiniStack/Floci ephemeral apply
        |              (existing)   (existing)          (G9, existing — new caller)
        v
   compose()  (existing, unmodified entry point once sub-project 2 fixes the zero-catalog path)
```

During sub-projects 1-5, this path runs *alongside* the existing catalog match, exercised only by
the parity-proving harness (sub-project 6) — never the default for a live `synthesize()` call
until parity is proven and the cutover happens.

## Correction (2026-07-21, after live testing)

Testing the loop live surfaced that `docs/phase7_item5_authoring_scope.md` — a scope doc this
design missed on first pass — already resolved Item 5's core architecture back on 2026-07-16:
**MinusOps never calls a model itself; the driving agentic CLI (Claude Code, Codex, "agy"/
Antigravity, etc.) authors the HCL, MinusOps only supplies context and gates the result.** Under
that architecture, sub-projects 2, 4, and most of 5's plumbing are **already built and working**,
confirmed by a live run this session (`aws_dynamodb_table`, `author-context` → hand-authored HCL →
`author --allow-incomplete` → composed with zero catalog modules → `tf_validate.py` clean). Status
per sub-project, corrected below. Sub-projects 3 and 6, and the dynamic-block gap in sub-project 1,
remain real, unbuilt work.

## Sub-projects (dependency order)

### 1. Module-shaped authoring + G2 dynamic-block support
**Status: partially done.** The module-shaped form (`authored_modules/<key>/`, with
`variable`/`output`, auto-wiring of `name_prefix`/`tags`, companion assets) already exists in
`synthesizer.py` (`_render_authored_module_call` and neighbors). **Still unbuilt:** G2's
`schema_lint.py` still unconditionally flags every `dynamic { ... }` block as
`unparseable_reference` (confirmed live, 2026-07-21) — this remains the real gap blocking
`table-format-iceberg` reproduction.
**Extends:** `core/generation/synthesizer.py`'s `authored_content` contract, `core/generation/schema_lint.py`'s `gate_content()`.
Today `authored_content` is `dict[str, str]` — one flat HCL blob per resource type, composed as
`authored_{type}.tf` at the composition root, no `variable`/`output`/`locals` boundary, no
companion-asset support. This item gives it a real module shape (survey §1, §4). It also fixes
G2's blanket rejection of `dynamic { ... }` blocks (`schema_lint.py`'s `_scan_body()` currently
treats every one as `unparseable_reference` by design) — required to reproduce
`table-format-iceberg`'s `dynamic "columns"` block, the corpus's only one.
**Done when:** the Phase 6 Step 5 regression harness's 5 named blockers
(`docs/phase6_step5_teardown_scope.md`) close for real against the extended mechanism, not via a
test-only workaround — including the 2 `path.module`-asset blockers and the 1 dynamic-block
blocker.

### 2. Fix `synthesize()`'s zero-catalog path
**Status: done.** `select_modules(explicit_ids=...)` now distinguishes `None` ("infer by keyword")
from `[]` ("explicitly zero catalog modules"), checked by identity not truthiness. Confirmed live,
2026-07-21: `synthesizer.py author aws_dynamodb_table --allow-incomplete ...` composed with
`"modules": []` through the real public `synthesize()` entry point, no `compose()` bypass needed.

### 3. Full-requirements-driven preplan
**Status: not built — this remains the real gap.** The live test above required manually declaring
`resource_type` + `justification` via `--allow-incomplete`; nothing today reads a full
`requirements.json` and derives that list itself. A function in `core/architecture/` (exact module
TBD in that sub-project's own plan)
that reads `requirements.json`'s complete schema — `functional`, all `data_pipeline` fields
(`sources`, `storage_zones`, `transforms`, `catalog`, `consumption`, `data_quality`,
`freshness_sla`, `governance`, `orchestration` — currently validated, never read downstream per
survey §3), all six NFR axes — and outputs a resource-type list. Field-by-field mapping (which
field influences which resource-type decision) is designed in that sub-project, not here.
**Done when:** a requirements record with a given `data_pipeline`/NFR shape deterministically
produces the same resource-type list, and changing a previously-inert field (e.g., `consumption`)
demonstrably changes the output.

### 4. Live per-type schema query
**Status: done.** `schema_watch.get_type_schema(provider, type_name, kind="resource")` already
composes `_fetch_schema()` + a raw block lookup (deliberately not `_reduce_full`, which strips
detail for a different, drift-comparison purpose). Confirmed live, 2026-07-21:
`synthesizer.py author-context aws_dynamodb_table ...` returned the real, current, full attribute
schema (including nested `block_types` like `global_secondary_index`, `point_in_time_recovery`)
straight from a real `terraform providers schema -json` call — not a synthetic fixture.
Deliberately uncached (schemas drift; a caller needing to avoid refetching must cache at its own
layer, per the function's own docstring). This *is* "the registry of all services" — the entire
AWS provider's schema comes back from one real `terraform providers schema -json` call against
the installed, version-pinned provider plugin; nothing here is scraped from a web docs page.
`discovery.py`'s `information_library.md`/`documentation_ledger.md` path stays reserved for
narrative/usage guidance (examples, gotchas, best practices), never for the attribute list itself
— the schema fetch is the only trusted source for "does this attribute exist."

**Dedup, before researching from scratch:** check for a prior record first, same "in-repo pattern
first" resolution order `discovery.py`'s docstring already states. Concrete order per resource
type: (1) does sub-project 6's parity-tracking store already have a clean-pass record for this
exact type? If so, reuse its authored HCL + provenance instead of re-authoring. (2) does
`discovery.py`'s existing `load_record(topic)` cache already have a saved doc-research record for
this type? Reuse the doc/URL set, but never the schema — the live schema fetch always re-runs
fresh regardless of cache hits, matching `modules.py`'s own stated principle that a grounding
example "is never staler than the catalog itself."
**Done when:** calling it for a type absent from every existing module (survey's own example:
`aws_dynamodb_table`) returns a real attribute table sourced from a live schema fetch, not a
synthetic test fixture; and calling it a second time for a type with an existing clean-pass record
returns the cached authored content without re-invoking the LLM.

### 5. Authoring + validate loop
**Status: core loop already built and proven live (2026-07-21), pre-authoring checklist and
emulator validation are not.** `assemble_authoring_context()` already assembles item 4's live
schema + `retrieve_grounding_examples()`'s real catalog content (confirmed: `retrieve_grounding_
examples()` DOES have a production caller now — this function — contrary to the survey's
"zero call sites" finding, which predates this). `synthesizer.py author-context`/`author` already
run the driving-agent loop end to end: this session fetched real context, hand-authored
`aws_dynamodb_table` HCL grounded in it, and it passed G2 + composed cleanly with zero catalog
modules, confirmed by `tf_validate.py` afterward. `write_authoring_record()` exists for the audit
trail (not exercised in this session's CLI path — needs confirming whether `_main_author` actually
calls it, or whether that wiring is itself a remaining gap).

**Still not built:** the pre-authoring checklist below (G5/G6/G9 pre-checks surfaced *before*
authoring, not just discovered after) and the G9 MiniStack/Floci ephemeral-apply step — this
session's run only went through G2 + offline `terraform validate`, no emulator apply. Given a
resource type and item 4's schema, the driving agent authors HCL into item 1's module-shaped seam,
grounded in that schema and `discovery.py`'s doc URLs plus the grounding examples. Before
authoring, the engine should resolve — and record — the following for the resource type, all
against real existing gates, not invented checks:

| Check | Source | Why it matters before writing |
|---|---|---|
| Required/optional attributes, types, deprecated flags | Item 4's live schema | What's actually valid to emit |
| G5 classification (stateful / IAM / reviewed-unsafe / auto-ship-eligible) | `core/governance/destructive_change_gate.py` | Known up front whether this can ever auto-ship or will always stage |
| G6 rule coverage (does a SEC-*/COST-* rule fire for this type?) | `policy/g6/rules.rego` | Author toward passing a known rule instead of failing validate blind |
| G9 emulator representability | `core/governance/ephemeral_apply.py`'s allowlist | Some types (e.g. `aws_sfn_state_machine`'s real `ValidateStateMachineDefinition` API call) have no honest emulator equivalent — this must be a disclosed carve-out in validate, not a silently-forever-failing check |
| Tag/naming convention | `compose()`'s existing `tags_all` wrapping (proven 2026-07-18) | Authored content must not duplicate what `compose()` already injects |
| Companion asset need | Item 1's asset-carrying mechanism | Detect when a type needs a script file (Glue-style `path.module` reference), not just HCL |
| Cross-resource wiring | New convention, this sub-project | When preplan produces multiple types for one pipeline, later authoring calls receive earlier ones' output identifiers so real references (e.g. a Glue job needing the bucket ARN) can be written, not left as `# REVIEW` stubs |

Validate then runs G2 (existing) → offline `terraform validate` (existing `tf_validate.py`) → a
G9 ephemeral apply (existing `ephemeral_apply.py`, `run_ephemeral_apply(..., emulator="ministack")`
then `"floci"`).

**Audit record**, same reviewable-JSON shape as `architecture_decision.json`/`module_provenance.py`
(never opaque model output): resource type; which requirements fields drove its selection
(preplan's own reasoning); the schema hash used (drift-detectable, same idea as G2's existing
`schema_hash`); which doc sources were cited; the G5/G6/G9 pre-checks above; G2/`terraform
validate`/MiniStack/Floci results; running clean-pass count.
**Done when:** at least one resource type not in any existing module's corpus is generated,
passes all three validation stages, and the record shows why (schema used, which docs cited,
emulator results, pre-checks resolved) — auditable the same way `architecture_decision.json` is.

### 6. Parity proof + cutover
**New:** a harness (parallel in spirit to `tests/test_teardown_regression_harness.py`) that runs
item 5 against every resource type the 16 catalog modules cover, recording a per-module retirement
record:
```json
{"module_id": "query-athena", "generation_attempts": 3, "clean_passes": 3,
 "status": "eligible_for_retirement", "retired_at": null}
```
`clean_passes` requires 3 consecutive attempts with zero manual correction, G2-clean,
`terraform validate`-clean, and clean on both MiniStack and Floci. Only once **every** module
shows `eligible_for_retirement` does a human review and sign off — then `modules/*/main.tf` is
deleted in one commit, `core/generation/modules.py`'s `MODULES` registry emptied, and
`synthesize()`'s default path becomes generation-only.
**Done when:** every one of the 16 modules has a clean-pass record and a human-signed retirement
commit removes them together.

## Error handling

Every stage stays fail-closed, matching the codebase's existing posture (G2/G5/G6/G9 all default
to blocking/staging on anything unrecognized or unverified, never silently passing):
- Preplan producing an empty or ambiguous resource-type list blocks composition with a clear
  reason, same as `requirements.py`'s existing completeness gate.
- Research failing (schema fetch error, unresolvable type) blocks authoring for that type — no
  fallback to memory/guessed attributes, ever.
- Authored HCL failing G2, `terraform validate`, or either emulator blocks that resource type's
  generation attempt from counting toward `clean_passes` — it's a failed attempt, logged, not
  silently retried into a false pass.
- The cutover itself is single-directional and reviewed: no module is deleted without an explicit
  human sign-off, regardless of how clean its automated record looks.

## Testing

- Each sub-project ships with its own unit tests (per existing repo convention — every `core/`
  module has a matching `tests/test_*.py`).
- Sub-project 6's parity harness doubles as the end-to-end test: it must reproduce, not just
  assert schemas, the same real proof style as `docs/generation_pivot_first_proof_2026-07-18.md`
  (real schema fetch, real `terraform plan`-equivalent check) — for all 16 modules, not one.
- The existing Phase 6 Step 5 regression harness (`tests/test_teardown_regression_harness.py`) is
  reused, not replaced, as the source of the 5 named structural blockers sub-project 1 must close.
